# 이름 채번, 캐시, 로그, 서버 환경 <Badge type="info" text="원본 분석" />

## 이름 채번

채번기 (eService Object Generator) 설정으로 `PRT-000001` 같은 이름을 받습니다. 채번기를 만드는 법과 번호가 늘어나는 방식은 [채번기](/trigger/generator) 에 있습니다.

### 채번기로 객체 만들기

이름을 받으면서 객체까지 만들고 그 id 를 돌려받습니다.

| 쓸 메서드 | 넘기는 값 | 돌려받는 것 |
| --- | --- | --- |
| `FrameworkUtil.autoName(context, type, policy)` | `type`: 타입의 **심볼릭 이름** (`"type_MyPart"`). 채번기 이름이기도 함. `policy`: 정책의 심볼릭 이름 | `String`. 프로그램이 돌려준 두 번째 값. OOTB 는 만든 객체의 id 로 씀 |
| `FrameworkUtil.autoName(context, type, series, policy, vault)` | `series`: 채번기의 리비전 (시리즈). 하나뿐이면 `""`. `vault`: 만들 vault. `null` 이면 `""` 로 넘김 | 위와 같음 |

```java
ContextUtil.startTransaction(context, true);
try {
    String newId = FrameworkUtil.autoName(context, "type_MyPart", "policy_MyPartPolicy");
    DomainObject.newInstance(context, newId).setAttributeValue(context, attrStatus, "Draft");
    ContextUtil.commitTransaction(context);
} catch (Exception e) {
    ContextUtil.abortTransaction(context);
    throw e;
}
```

- 안에서 MQL `execute program $1 $2 $3 $4 $5 $6 $7` 로 `eServicecommonNumberGenerator.tcl` 에 `type`, `series`, `policy`, `Null`, `vault`, 리비전 (`""`) 을 넘깁니다. 프로그램 결과를 `|` 로 잘라 첫 값이 `1` 이면 `emxFramework.Error.CreatingObjectType` 문구 + `type` 으로, 결과가 비면 `emxFramework.Error.NoResultsFound` 문구로 예외입니다 (`FrameworkException`). 아니면 두 번째 값을 돌려줍니다.
- 프로그램 원본이 분석한 OOTB 파일에 없어서, 객체를 어떻게 만들고 무엇을 돌려주는지는 OOTB 사용 예로만 확인했습니다 <Badge type="danger" text="검증 필요" />. OOTB 는 돌려받은 값을 `setId` 나 `newInstance` 에 넣습니다.
- 객체가 바로 만들어지므로 뒤의 속성 설정, 연결과 한 트랜잭션으로 묶습니다.
- 실제 이름만 있으면 `FrameworkUtil.getAliasForAdmin(context, "type", 실제이름, true)` 로 심볼릭 이름을 얻어 넘깁니다 ([스키마 이름, 타입·정책·속성 정보](/jpo/api/util/schema)).
- 채번기가 없는 타입이면 예외입니다.

### 채번기로 이름만 받기

객체는 직접 만들고 이름만 채번기로 받을 때 씁니다. 자세한 사양은 [getAutoGeneratedName](/jpo/api/domain-object#getautogeneratedname) 에 있습니다.

| 쓸 메서드 | 넘기는 값 | 돌려받는 것 |
| --- | --- | --- |
| `DomainObject.getAutoGeneratedName(context, generator, series)` | `generator`: 채번기 이름 (타입의 심볼릭 이름). `series`: 시리즈. 보통 `""` | `String`. 만든 이름 |

```java
String name = DomainObject.getAutoGeneratedName(context, "type_MyPart", "");
```

- 같은 프로그램 (`eServicecommonNumberGenerator.tcl`) 의 8 번째 자리에 `Yes` 를 넘깁니다. `autoName` 8 개 인자 형태의 첫 `boolean` 이 같은 자리로 갑니다. OOTB `emxProjectBudgetBase_mxJPO.java` 는 그 인자에 `//boolean uniqueNameOnly` 라고 주석을 달고 `true` 로 받은 값을 이름으로 씁니다. 프로그램 원본으로는 확인하지 못했습니다 <Badge type="danger" text="검증 필요" />.

**같은 일을 하는 다른 메서드**

| 메서드 | 쓰지 않는 이유 |
| --- | --- |
| `FrameworkUtil.autoName(context, type, series, policy)` | 5 개 인자 형태에서 `vault` 만 뺀 것 |
| `FrameworkUtil.autoName(context, type, series, policy, vault, customRev)` | 프로그램 6 번째 자리에 `customRev` 를 더 넘김. OOTB 는 만들 객체의 리비전 (`revision`, `"-"`) 을 넘김 (2 건) |
| `autoName(…, boolean)` 네 형태 | `false` 면 `boolean` 없는 형태와 같음. `true` 면 `UICache.getObjectGenerator` 로 채번기를 찾아 넘기고, 그 값이 `Name Generator` 면 `eServicecommonNameGenerator.tcl` 을 부름. OOTB 1 건 (7 개 인자) |
| `autoName(context, type, series, policy, vault, customRev, uniqueNameOnly, useSuperUser)` | 두 `boolean` 을 프로그램 8, 9 번째 자리에 `Yes` / `No` 로 넘김 (이름은 OOTB 주석). OOTB 는 첫 값이 `true` 면 받은 값을 이름으로, `false` 면 id 로 씀 (15 건). 프로그램이 하는 일은 확인 못 함 |
| `FrameworkUtil.autoRevision(context, type, name, policy, vault)` | 다른 일. 이름을 넘기고 `eServicecommonRevisionGenerator.tcl` 을 부름. OOTB 는 조직 객체 3 곳에서 받은 값을 id 로 씀 |
| `obj.getUniqueName(prefix)` | 채번기 없이 접두어 + 카운터 + 지금 시각을 이어 붙임. DB 에서 겹치는지 확인하지 않음 ([getUniqueName](/jpo/api/domain-object#getuniquename)) |
| `obj.getShortUniqueName(prefix)` | 위와 같고 시각을 뒤 10 자리만 씀 |

::: info 근거
xerinfra.jar `FrameworkUtil.autoName`: 3 개 인자 `(type, policy)` → 6 개 인자 `(type, null, policy, null, null)`. 4, 5 개 인자는 `null` 인 `series`, `vault` 를 `""` 로 바꿔 6 개 인자로. 6 개 인자 형태는 `"execute program $1 " + "$2" + " " + "$3" + " " + "$4" + " $5 " + "$6" + " " + "$7"` (상수 풀에서 공백 확인) 에 `[eServicecommonNumberGenerator.tcl, type, series, policy, "Null", vault, revision]`, 결과를 `trim` 해 `StringTokenizer(결과, "|")`, 첫 값이 `"1"` 이면 `CreatingObjectType`, 비면 `NoResultsFound` (`MatrixException` 을 `FrameworkException` 으로 감쌈), 두 번째 값 반환. `boolean` 7 개 인자 형태는 `false` 면 6 개 인자, `true` 면 `UICache.getObjectGenerator(context, type, series)` 결과가 `"Name Generator"` 면 `eServicecommonNameGenerator.tcl` 에 5 개, 아니면 `eServicecommonNumberGenerator.tcl` 에 `[생성기, series, policy, "Null", vault, revision, type]`. 8 개 인자 형태는 같은 9 개 값 뒤에 두 `boolean` 을 `Yes`/`No` 로 (Name Generator 면 `TRUE`/`FALSE`). `autoRevision` 은 `eServicecommonRevisionGenerator.tcl` 에 `(type, name, policy[, vault])`. `DomainObject.getAutoGeneratedName` 은 `[eServicecommonNumberGenerator.tcl, generator, series, " " ×5, "Yes"]`. OOTB 인자 개수: 3 개 36, 5 개 11, 8 개 15, 6 개 2, 4 개 1, 7 개 1. OOTB 예: ENOConditionalQuestionnaireBase_mxJPO.java, emxDocumentCentralSubscriptionBase_mxJPO.java (받은 값을 `setId`), emxCPNCharacteristicListBase_mxJPO.java (`false, true` 뒤 `setId`), emxProjectBudgetBase_mxJPO.java (인자마다 `//String revision`, `//String customRev`, `//boolean uniqueNameOnly`, `//boolean useSuperUser` 주석, `true, false` 로 받은 값을 이름으로 씀), emxBusinessUnitBase_mxJPO.java, emxLocationBase_mxJPO.java, emxRegionBase_mxJPO.java (`autoRevision`)
:::

## 서버 전체 캐시

여러 요청이 같이 쓰는 값을 서버 메모리에 둡니다. 자주 읽고 거의 바뀌지 않는 값 (설정 목록 ...) 을 매번 MQL 로 읽지 않으려고 씁니다.

| 쓸 메서드 | 넘기는 값 | 돌려받는 것 |
| --- | --- | --- |
| `CacheUtil.getCacheObject(context, key)` | `key`: 캐시 키 | `Object`. 없으면 `null` |
| `CacheUtil.setCacheObject(context, key, value)` | `value`: 넣을 값. 같은 키가 있으면 바꿈 | 없음 |
| `CacheUtil.removeCacheObject(context, key)` | `key`: 지울 키 | `Object`. 지운 값, 없었으면 `null` |

```java
String key = "XX_MyApp.PolicyList";
StringList policies = (StringList) CacheUtil.getCacheObject(context, key);
if (policies == null) {
    policies = FrameworkUtil.split(MqlUtil.mqlCommand(context, "list policy $1", "My*"), "\n");
    CacheUtil.setCacheObject(context, key, policies);
}
```

::: warning 모든 사용자가 같이 씁니다
값은 서버 (JVM) 의 static Map 에 테넌트별로 들어갑니다. 요청이나 사용자에 따라 달라지는 값 (권한, 언어별 문구) 을 넣으면 다른 사용자에게 그대로 보입니다. 서버를 여러 대로 돌리면 서버마다 따로 쌓입니다. 바뀔 수 있는 값은 `removeCacheObject` 로 비울 때를 정해 둡니다.
:::

- 서버에 가지 않고 메모리만 씁니다. 만료 시간이 없어서 지우지 않으면 서버를 다시 띄울 때까지 남습니다.
- 테넌트 이름은 `context.getTenant()` 이고, 비어 있으면 `_GLOBAL_NO_TENANT_` 입니다. 테넌트마다 따로인 Map 이 있습니다.
- 키는 다른 앱과 겹치지 않게 앞에 앱 이름을 붙입니다. OOTB 에는 `"invokeFrom"`, `"typeList"` 처럼 짧은 키와, `사용자이름 + "_QuestionsResponse"` 처럼 사용자 이름을 붙인 키가 섞여 있습니다.
- 꺼낸 값 (위의 `StringList`) 을 고치면 캐시 안의 값이 바로 바뀝니다. 같은 객체를 돌려주기 때문입니다.

**같은 일을 하는 다른 메서드**

| 메서드 | 쓰지 않는 이유 |
| --- | --- |
| `CacheUtil.getCacheString(context, key)` | `getCacheObject` 결과를 `String` 으로 형변환만 함. 다른 형이면 `ClassCastException` |
| `CacheUtil.getCacheMap(context, key)`, `getCacheMap(context, key, weak)` | `Map` 으로 형변환. 없으면 새 빈 `HashMap` (`weak` 가 `true` 면 `WeakHashMap`) 을 돌려주지만 **캐시에 넣지 않음**. 고친 뒤 `setCacheMap` 을 따로 불러야 함 |
| `CacheUtil.getCacheMapList(context, key)` | `MapList` 로 형변환. 없으면 새 빈 `MapList` 를 돌려주고 캐시에 넣지 않음 |
| `CacheUtil.setCacheMap(context, key, map)` | 안에서 `setCacheObject` 를 그대로 부름 |
| `CacheUtil.clearCache(context)` | 그 테넌트의 캐시를 **모두** 지움. OOTB 키도 함께 지워짐. OOTB 미사용 |

자세히: [서버 전체 캐시 (CacheUtil)](/jpo/utils#서버-전체-캐시-cacheutil)

::: info 근거
xerinfra.jar `CacheUtil`: static `_GLOBAL_CACHE` 는 `LinkedHashMap` 하위 클래스 (`removeEldestEntry` 는 크기 10000 초과일 때. 키는 테넌트 이름). `getTenantMap` 은 `_lock` 으로 동기화해 테넌트 Map (`Collections.synchronizedMap(new HashMap())`) 을 꺼내거나 만듦. `getCacheObject` → `get`, `removeCacheObject` → `remove`, `setCacheObject` 는 `_lock` 안에서 `put` 뒤 테넌트 Map 을 다시 넣음. `getTenantName` 은 `context.getTenant()`, `null`/`""` 면 `_GLOBAL_NO_TENANT_`. `getCacheString` 은 `(String)` 형변환, `getCacheMap(…, weak)` 는 없으면 `synchronizedMap(new WeakHashMap())` 또는 `new HashMap()` 을 돌려주기만 함, `getCacheMapList` 는 `new MapList()`. `setCacheMap` → `setCacheObject`. `clearCache` → `_GLOBAL_CACHE.remove(테넌트)`. 폐기 표시 없음. OOTB 키 예: emxProjectSpaceBase_mxJPO.java (`CacheUtil.getCacheObject(context, loggedInUser+"_QuestionsResponse")`, `"QuestionsResponse"`)
:::

## 로그 남기기

새 코드는 slf4j `Logger` 로 남깁니다. 레벨 (`debug`, `info`, `error`) 을 고를 수 있고 서버의 로그 설정을 따릅니다. 3dspace 의 `WEB-INF/lib` 에 `slf4j-api.jar` 가 있어 jar 를 따로 넣지 않아도 됩니다.

| 쓸 것 | 넘기는 값 | 돌려받는 것 |
| --- | --- | --- |
| `LoggerFactory.getLogger(XX_UtilEtc_mxJPO.class)` | 이 JPO 클래스 | `org.slf4j.Logger`. 클래스에 `static final` 로 하나 둠 |
| `LOG.info(msg, args...)`, `LOG.error(msg, e)` | `msg`: `{}` 자리에 `args` 가 들어가는 문구. `e`: 예외 (스택까지 남김) | 없음 |

```java
private static final Logger LOG = LoggerFactory.getLogger(XX_UtilEtc_mxJPO.class);

public void promotePart(Context context, String[] args) throws Exception {
    Map programMap = (Map) JPO.unpackArgs(args);
    String objectId = (String) programMap.get("objectId");
    try {
        DomainObject.newInstance(context, objectId).promote(context);
        LOG.info("promoted {}", objectId);
    } catch (Exception e) {
        LOG.error("promote failed: " + objectId, e);
        throw e;
    }
}
```

- 출력 위치는 서버의 로그 설정을 따릅니다. 설정 파일은 분석한 소스에 없어서 서버에서 확인합니다.
- OOTB 는 `emxCommonDocumentBase_mxJPO.java` 가 `LoggerFactory.getLogger` 를, `ENOGLSFormulationTypeUIBase_mxJPO.java` 등 8 개 파일이 `XLoggerFactory.getXLogger` (slf4j-ext) 를 씁니다.
- 표 행마다 도는 곳 (열 function) 에서 행마다 로그를 찍지 않습니다.

DebugUtil 은 아래처럼 동작합니다 (로컬 실행으로 확인).

| 호출 | 표준 출력 |
| --- | --- |
| `DebugUtil.debug("hidden")` (처음 상태) | 아무것도 찍지 않음 |
| `DebugUtil.setDebug(true)` 뒤 `DebugUtil.debug("J\|", "two", " parts")` | `J\|two parts` |
| 위 상태에서 `DebugUtil.debug(null)` | `null` |
| `DebugUtil.setDebug(false)` 뒤 `DebugUtil.debug("hidden again")` | 아무것도 찍지 않음 |

**같은 일을 하는 다른 메서드**

| 메서드 | 쓰지 않는 이유 |
| --- | --- |
| `DebugUtil.debug(msg)` (인자 1 ~ 3 개) | 켜고 끄는 값이 서버 (JVM) 전체에 하나뿐 (`setDebug`). 켜면 OOTB 의 `DebugUtil.debug` 407 곳도 함께 찍힘. 레벨 없이 `System.out` 으로 나감 |
| `DebugUtil.setDebug(on)` | 위 스위치. OOTB JPO 에서는 주석 안 1 곳뿐 |
| `System.out.println(msg)`, `e.printStackTrace()` | 레벨 없이 항상 찍혀 운영 로그가 커짐 |
| `new BufferedWriter(new MatrixWriter(context))` 의 `write` | 받은 글자를 서버 세션 쪽 `writeString` 으로 넘김. OOTB 이관 JPO 의 `mqlLogWriter` 가 MQL 에서 돌릴 때 진행 상황을 찍는 데 씀. 화면에서 부른 JPO 에서 어디로 가는지는 확인 못 함 |
| `DomainObject.debug(...)` <Badge type="warning" text="폐기" /> | 폐기, protected ([debug](/jpo/api/domain-object#debug)) |
| `emxContextUtil_mxJPO.mqlNotice(context, msg)` | 로그가 아니라 사용자 화면 메시지 ([MQL 실행, 환경 변수](/jpo/api/util/mql)) |

자세히: [로그](/jpo/i18n-exception#로그)

::: info 근거

## 백그라운드로 실행하기

오래 걸리는 일 (알림 보내기, 보고서 만들기) 을 사용자 요청과 떼어 다른 스레드에서 돌립니다. OOTB 트랜잭션 알림 트리거가 이렇게 씁니다.

| 쓸 메서드 | 넘기는 값 | 돌려받는 것 |
| --- | --- | --- |
| `new BackgroundProcess().submitJob(context, program, method, args, (String) null)` | `program`: JPO 이름 (`_mxJPO` 뺀 것). `method`: 부를 메서드. `args`: 그 메서드에 넘길 `String[]` (`JPO.packArgs(map)`). 마지막: Job 객체 id. 쓰지 않으면 `(String) null` | 없음. 바로 돌아옴 |

```java
Map params = new HashMap();
params.put("objectId", objectId);
new BackgroundProcess().submitJob(context, "XX_UtilEtc", "writeReport", JPO.packArgs(params), (String) null);
```

- 마지막 `null` 은 `(String) null` 로 씁니다. 그냥 `null` 이면 `submitJob(Context, Object, String, Object[], Class[])` 와 겹쳐 컴파일 오류 (`reference to submitJob is ambiguous`) 입니다 (javac 로 확인).
- `context.getFrameContext("background job")` 로 새 context 를 받아, 스레드 풀 (설정 `emxFramework.BackgroundProcess.NumberOfThreads`, 분석한 값 `10`) 에서 2 초 뒤에 `JPO.invoke(context, program, …, method, args)` 의 `int` 형태로 부릅니다. OOTB 의 대상 메서드 (`notifyInBackground`) 도 `int` 를 돌려줍니다.
- 끝나면 그 context 를 `shutdown` 합니다. 대상 메서드의 예외는 스택만 찍히고 부른 쪽은 알 수 없습니다. 결과가 필요하면 대상 메서드가 객체에 남기거나 [알림](/jpo/api/util/mail) 을 보냅니다.
- 새 context 로 돌므로 부른 쪽 트랜잭션과 묶이는지, 새 context 의 사용자가 누구인지는 확인하지 못했습니다 <Badge type="danger" text="검증 필요" />. 부른 쪽이 아직 commit 하지 않은 변경을 읽어야 하는 일은 넘기지 않습니다.

**같은 일을 하는 다른 메서드**

| 메서드 | 쓰지 않는 이유 |
| --- | --- |
| `submitJob(context, DomainObject, method, Object[], Class[])` <Badge type="warning" text="폐기" /> | 폐기 |
| `submitJob(context, Object, method, Object[], Class[])` | JPO 이름 대신 Java 객체의 메서드를 리플렉션으로 부름 |
| `invokeInBackground(context, program, method, args, jobId)` | `submitJob` 이 스레드 안에서 부르는 메서드. 바로 부르면 지금 스레드에서 돎 |
| `new Job(program, method, args).createAndSubmit(context)` | DB 에 Job 객체를 만들고 (안에서 `autoName`) 상태로 실행을 관리함. 객체가 남음. 진행 상황을 화면에 보여 줄 때만 |

::: info 근거
xerinfra.jar `BackgroundProcess.submitJob(Context, String, String, String[], String)`: `BackgroundProcessThread(this, context, new BackgroundProcess(), "invokeInBackground", [context, program, method, args, jobId], …)` 를 `getThreadPool(context).execute`. 스레드 생성자는 `context.getFrameContext("background job")`, `run` 은 `Thread.sleep(2000)` 뒤 리플렉션 호출. `getThreadPool` 은 `emxFramework.BackgroundProcess.NumberOfThreads` (비면 `10`) 로 `Executors.newFixedThreadPool`. `invokeInBackground` 는 `jobId` 가 있을 때만 Job 객체를 기다리고, `JPO.invoke(context, program, JPO.packArgs({"Job ID": jobId}), method, args)` (반환형 `int`), 끝나면 `context.shutdown()`, 예외는 `printStackTrace`. `submitJob(Context, DomainObject, …)` 에 `Deprecated`. `Job.create` 는 `FrameworkUtil.autoName(… 8 개)` 로 객체를 만들고 속성과 연결을 넣음, `submit` 은 `setState`. OOTB 예: emxTransactionNotificationUtilBase_mxJPO.java (`submitJob(context, "emxTransactionNotificationUtil", "notifyInBackground", args, (String) null)`). properties/emxSystem.properties:3443
:::
