# 객체 생성, 수정 <Badge type="info" text="원본 분석" />

객체를 만들고, 값과 상태를 바꾸고, 관계를 연결하는 메서드입니다. 넘기는 값은 모두 문자열이고, 타입 / 관계 / 속성 / 상태 이름은 실제 이름을 넘깁니다. 예제의 `part`, `relPartDocument` 같은 변수는 [예제에서 쓰는 변수](/jpo/api/#예제에서-쓰는-변수) 에 있습니다.

::: info 근거
시그니처와 동작은 xerinfra.jar `DomainObject`, `DomainRelationship`, eMatrixServletRMI.jar `BusinessObject` class 파일 (javap) 기준. 건수는 jpo 폴더 바로 아래 1,615 개 파일에서 센 호출 수: `.setAttributeValue(context` 955, `DomainRelationship.connect(context` 549, `.setAttributeValues(context` 298, `.setState(context` 136, `.setDescription(context` 111, `.promote(context` 99, `.setOwner(context` 75, `.createObject(context` 64, `DomainRelationship.setAttributeValue(context` 54, `DomainRelationship.setToObject(context` 38, `.setName(context` 29, `.createAndConnect(context` 25, `.setPolicy(context` 20, `.cloneObject(context` 13, `.demote(context` 13, `.reviseObject(context` 12
:::

샘플: [XX_ObjectApi_mxJPO.java](https://github.com/LeeOuHyoun/3d-docs/blob/main/JPOSample/XX_ObjectApi_mxJPO.java) 의 `createDocument`, `updatePart`, `updateQuantity`, `releasePart`, `revisePart` ([메서드별 설명](/jpo/api/#샘플-jpo))

## 한눈에 보기

| 하고 싶은 일 | 메서드 |
| --- | --- |
| 객체 만들기 | `obj.createObject(context, type, name, revision, policy, vault)` |
| 만들면서 바로 연결하기 | `obj.createAndConnect(context, type, rel, other, isFrom)` |
| 다음 리비전 만들기 | `obj.reviseObject(context, withFiles)` |
| 복사본 만들기 | `obj.cloneObject(context, newName)` |
| 속성 바꾸기 | `obj.setAttributeValue(context, 속성이름, 값)`, `obj.setAttributeValues(context, map)` |
| 설명, 소유자, 이름 바꾸기 | `obj.setDescription`, `obj.setOwner`, `obj.setName` |
| 상태 바꾸기 | `obj.promote(context)`, `obj.demote(context)`, `obj.setState(context, 상태)` |
| 두 객체 연결하기 | `DomainRelationship.connect(context, from, rel, to)` |
| 관계 속성 바꾸기 | `DomainRelationship.setAttributeValue(context, relId, 속성이름, 값)` |
| 여러 변경을 함께 되돌릴 수 있게 묶기 | `ContextUtil.startTransaction(context, true)` |

## 생성

| 메서드 | 하는 일 | 돌려받는 것 |
| --- | --- | --- |
| `obj.createObject(context, type, name, revision, policy, vault)` | 객체를 만듦. 끝나면 `obj` 가 새 객체를 가리킴 | `void`. 새 id 는 `obj.getId(context)` |
| `obj.createAndConnect(context, type, rel, other, isFrom)` | 객체를 만들고 바로 `other` 와 연결함. `isFrom` 이 `true` 면 `other → 새 객체`, `false` 면 `새 객체 → other` | `DomainRelationship` (만든 관계) |
| `obj.reviseObject(context, withFiles)` | **마지막 리비전** 의 다음 리비전을 만듦. `withFiles` 가 `true` 면 파일을 새 리비전으로 이어 받음 | `BusinessObject` (새 리비전) |
| `obj.cloneObject(context, newName)` | 복사본을 만듦 (파일 포함). `newName` 이 `null` 이면 이름을 자동으로 붙임. 타입에 자동 채번 설정 (`AutoGeneratedObjectName`) 이 있으면 넘긴 이름도 채번 이름으로 바뀜 ([cloneObject](/jpo/api/domain-object#cloneobject)) | `BusinessObject` (복사본) |
| `DomainObject.getAutoGeneratedName(context, "type_X", "")` | 타입의 채번기 프로그램 (`eServicecommonNumberGenerator.tcl`) 을 실행해 이름을 받음. 첫 인자는 심볼릭 타입 이름. 프로그램이 객체도 만드는지는 <Badge type="danger" text="검증 필요" /> | `String` |

`createObject` 와 `createAndConnect` 는 [빈 객체](/jpo/api/read#객체-얻기) (`DomainObject.newInstance(context)`) 에서 부릅니다. `createObject` 에 `null` 을 넘긴 인자는 아래 기본값을 씁니다. `""` 를 빈 값으로 보는 것은 `name` 뿐이고, `revision`, `policy`, `vault` 에 `""` 를 넘기면 그대로 서버로 갑니다.

| 인자 | 비었을 때 |
| --- | --- |
| `name` (`""`, 공백뿐도) | 고유 이름 (`auto_...`) 을 만들어 붙임 |
| `revision` | 정책의 첫 리비전 |
| `policy` | 타입의 기본 정책 |
| `vault` | 로그인 context 의 vault. `createAndConnect` 는 `other` 의 vault |

```java
DomainObject doc = DomainObject.newInstance(context);
doc.createObject(context, typeDocument, null, null, null, null);
String newId = doc.getId(context);

DomainObject doc2 = DomainObject.newInstance(context);
DomainRelationship rel = doc2.createAndConnect(context, typeDocument, relPartDocument, part, true);
String relId = rel.getName();

String nextRevisionId = part.reviseObject(context, false).getObjectId(context);
```

- 만든 관계의 id 는 `rel.getName()` 으로 꺼냅니다.
- `createObject`, `createAndConnect`, `reviseObject`, `cloneObject` 는 모두 안에서 트랜잭션을 열고 닫습니다. 바깥에 트랜잭션이 있으면 그 안에 묶입니다 ([여러 변경을 한 묶음으로](#여러-변경을-한-묶음으로)).
- 채번기로 이름을 붙여 만들려면 `FrameworkUtil.autoName` 을 씁니다 ([채번기](/trigger/generator)).

::: info 근거
xerinfra.jar `DomainObject.createObject`: 이름이 `null` 이거나 trim 해서 비면 `getDefaultName` → `getUniqueName`, `getDefaultPolicy`, `getDefaultRevision`, `getDefaultVault` 뒤 `BusinessObject.create`. `createAndConnect(context, type, rel, other, isFrom)` → `(context, type, name=null, rel, other, isFrom)` → `(context, type, name, revision=null, policy=null, vault=null, rel, other, isFrom)`: `startTransaction`, vault 가 비면 `getDefaultVault(context, other)`, `createObject`, `connect(context, rel, other, isFrom)`, `commitTransaction`. `reviseObject(context, withFiles)` 는 `getLastRevision` 으로 얻은 객체에 `getNextSequence` 와 `revise(context, visuals, 다음리비전, vault, withFiles)`. `cloneObject(context, name)` 는 `cloneObject(context, name, null, null, true)` (파일 복사), 이름이 비면 `getDefaultName`, 타입의 admin property `AutoGeneratedObjectName` 이 `true` 면 `getAutoGeneratedName`. 관계 id: `Relationship(String)` 생성자가 id 를 이름으로 두고, emxTaskBase_mxJPO.java:11230 (`sRelId = domRel.getName()`). 호출 예: emxCommonEngineeringChangeBase_mxJPO.java:8050 (`reviseObject(context, inheritFiles)`), emxControlledFolderBase_mxJPO.java:555
:::

## 값 수정

| 메서드 | 하는 일 | 돌려받는 것 |
| --- | --- | --- |
| `obj.setAttributeValue(context, 속성이름, 값)` | 속성 하나를 바꿈 | `void` |
| `obj.setAttributeValues(context, map)` | 속성 여러 개를 한 번에 바꿈. `map` 은 속성 이름 → 값 | `void` |
| `obj.setDescription(context, 설명)` | 설명을 바꿈 | `void` |
| `obj.setOwner(context, 사용자이름)` | 소유자를 바꿈. 폐기된 `changeOwner` 도 같은 일 | `void` |
| `obj.setName(context, 이름)` | 이름을 바꿈. 지금 이름과 같으면 아무것도 안 하고, `null` 이면 예외. `""` 는 검사하지 않으므로 미리 확인 | `void` |
| `obj.setPolicy(context, 정책이름)` | 정책을 바꿈. 폐기된 `changePolicy` 도 같은 일 | `void` |
| `obj.setVault(context, vault이름)` | vault 를 바꿈 | `void` |
| `MqlUtil.mqlCommand(context, "modify bus $1 $2 $3", id, 속성이름, 값)` | MQL 로 직접 바꿈 ([MQL](/jpo/api/util/mql)) | `String` |

```java
Map attrs = new HashMap();
attrs.put(attrStatus, "Approved");
part.setAttributeValues(context, attrs);
part.setDescription(context, "검토 완료");
part.setOwner(context, context.getUser());
```

- 속성을 둘 이상 바꿀 때는 `setAttributeValue` 를 여러 번 부르지 말고 `setAttributeValues` 로 한 번에 넘깁니다.
- 날짜 속성에는 `MM/dd/yyyy hh:mm:ss a` 형식 문자열을 넘깁니다 ([날짜](/jpo/api/util/date)).
- 로그인 사용자에게 수정 권한이 없으면 예외가 납니다. 시스템이 대신 바꿔야 하면 [pushContext](/jpo/transaction-context#슈퍼유저로-바꾸기-pushcontext) 로 감쌉니다.

::: info 근거
xerinfra.jar `DomainObject`: `setAttributeValue` 는 `Attribute` 하나를 담은 `AttributeList` 로 `setAttributes`, `setAttributeValues(Context, Map)` 는 `FrameworkUtil.toAttributeList(map)` 으로 한 번에 넘김. `setDescription`, `setOwner` 는 값을 넣고 `update(context)`. `setName` 은 이름이 `null` 이면 `emxFramework.Beans.DomainObject.ObjectNameCantBeNull` 예외, 지금 이름과 같으면 건너뛰고, 아니면 `change(context, type, 새이름, revision, vault, policy)`. `setPolicy` 도 `change`. `changeOwner` → `setOwner`, `changePolicy` → `setPolicy`
:::

## 상태 바꾸기

| 메서드 | 하는 일 | 돌려받는 것 |
| --- | --- | --- |
| `obj.promote(context)` | 다음 상태로 한 단계 올림 | `void` |
| `obj.demote(context)` | 이전 상태로 한 단계 내림 | `void` |
| `obj.setState(context, 상태이름)` | 그 상태가 될 때까지 promote 나 demote 를 되풀이함. 정책에 없는 상태면 예외 | `int`. 움직인 단계 수 |
| `obj.setState(context, 상태이름, false)` | 위와 같고 promote 할 때마다 먼저 `LifeCycleUtil.checksToPromoteObject` 를 부름 | `int`. 움직인 단계 수 |

```java
String policy = part.getInfo(context, DomainConstants.SELECT_POLICY);
String release = PropertyUtil.getSchemaProperty(context, "policy", policy, "state_Release");
int moved = part.setState(context, release);
```

- `setState` 가 돌려주는 값은 올린 단계 수면 양수, 내린 단계 수면 음수, 이미 그 상태였으면 `0` 입니다.
- 상태 이름은 실제 이름입니다. 위 예제처럼 정책 이름과 심볼릭 상태 이름 (`state_Release`) 으로 얻습니다.
- promote, demote 에는 정책의 상태 트리거가 걸립니다. 트리거가 막으면 예외가 납니다 ([라이프사이클과 promote](/trigger/lifecycle)).

::: info 근거
xerinfra.jar `DomainObject.setState(context, state)` → `setState(context, state, true)`. 정책 상태 목록에서 현재 위치와 목표 위치를 찾고, 없으면 `emxFramework.Beans.DomainObject.StateNotFound` 문구로 `FrameworkException`. 목표가 뒤에 있으면 `promote` 를 되풀이 (세 번째 인자가 `false` 면 그 전에 `LifeCycleUtil.checksToPromoteObject`), 앞에 있으면 `demote`. 한 단계마다 `current` 를 읽어 목표에 닿으면 멈추고, 목표를 지나쳤을 때만 `PromotionFailed` / `DemotionFailed` 예외 (상태가 바뀌지 않아도 예외 없이 처음 계산한 횟수만큼 되풀이). 반환은 목표 위치 - 현재 위치
:::

## 연결

두 객체 사이에 관계를 만듭니다. 방향 표기 `A → B` 는 A 가 from 쪽 (부모), B 가 to 쪽 (자식) 이라는 뜻입니다 ([관계의 방향](/jpo/api/#_3-관계에는-방향이-있습니다)).

| 메서드 | 만들어지는 방향 | 돌려받는 것 |
| --- | --- | --- |
| `DomainRelationship.connect(context, a, rel, b)` | `a → b` | `DomainRelationship` |
| `a.connectTo(context, rel, b)` <Badge type="warning" text="폐기" /> | `a → b` | `DomainRelationship` |
| `a.connectFrom(context, rel, b)` <Badge type="warning" text="폐기" /> | `b → a` | `DomainRelationship` |
| `a.connect(context, rel, b, false)` <Badge type="warning" text="폐기" /> | `a → b` | `DomainRelationship` |
| `a.connect(context, rel, b, true)` <Badge type="warning" text="폐기" /> | `b → a` | `DomainRelationship` |
| `a.addToObject(context, new RelationshipType(rel), bId)` | `a → b` | `DomainRelationship` |
| `a.addFromObject(context, new RelationshipType(rel), bId)` | `b → a` | `DomainRelationship` |
| `DomainRelationship.connect(context, aId, rel, bId, false)` | `a → b`. 객체 id 로 연결 | `void` |
| `DomainRelationship.connect(context, a, rel, true, bIds)` | `a → 각 b`. 여러 개를 한 트랜잭션으로 | `Map` (b 의 id → 관계 id) |
| `DomainRelationship.connect(context, a, rel, false, bIds)` | `각 b → a`. 여러 개를 한 트랜잭션으로 | `Map` (b 의 id → 관계 id) |

`a`, `b` 는 `DomainObject`, `aId`, `bId` 는 객체 id (`String`), `bIds` 는 객체 id 배열 (`String[]`), `rel` 은 관계의 실제 이름입니다. <Badge type="warning" text="폐기" /> 가 붙은 형태는 안에서 `DomainRelationship.connect(context, from, rel, to)` 를 부르므로 그것을 씁니다 ([연결](/jpo/api/domain-object#연결)).

::: warning 같은 true 라도 방향이 다릅니다
`DomainRelationship.connect(context, a, rel, true, bIds)` 의 `true` 는 `a` 가 from 쪽이라는 뜻입니다. `a.connect(context, rel, b, true)` (폐기) 와 `createAndConnect(..., other, true)` 의 `true` 는 **넘긴 객체** (`b`, `other`) 가 from 쪽이라는 뜻입니다. 헷갈리면 방향이 인자 순서에 그대로 드러나는 `DomainRelationship.connect(context, from, rel, to)` 를 씁니다.
:::

```java
DomainRelationship rel = DomainRelationship.connect(context, part, relPartDocument, doc);
rel.setAttributeValue(context, attrQty, "2");
String relId = rel.getName();

Map relIdByDocId = DomainRelationship.connect(context, part, relPartDocument, true, docIds);
```

- `doc` 은 문서 객체 (`DomainObject`), `docIds` 는 문서 id 배열 (`String[]`) 입니다.
- `DomainRelationship.connect(context, aId, rel, bId, preserve)` 의 마지막 인자가 `true` 면 MQL `connect` 에 `preserve` 를 붙여 실행합니다.

::: info 근거
xerinfra.jar: `DomainRelationship.connect(context, from, rel, to)` 는 두 객체를 열고 트랜잭션 안에서 `from.connect(context, relType, true, to)` (`BusinessObject.connect` 의 세 번째 인자 `true` = 호출한 객체가 from). `DomainRelationship.connect(context, obj, relType, isFrom, ids, ...)` 는 id 마다 `obj.connect(context, relType, isFrom, 상대)` 를 부르고 `상대 id → Relationship.getName()` 을 Map 에 담음. `DomainObject.connect(context, rel, other, isFrom)` 는 `isFrom` 이면 `addFromObjects` (= `DomainRelationship.connect(context, other, rel, this)`), 아니면 `addToObjects` (= `connect(context, this, rel, other)`). `connectTo` → `addToObjects`, `connectFrom` → `addFromObjects`. `addToObject(context, relType, id)` 는 `connect(context, this, relType, new DomainObject(id))`, `addFromObject` 는 그 반대. `connect(Context, String, String, String, boolean)` 은 MQL `connect businessobject $1 relationship $2 to $3`, `preserve` 면 `connect businessobject $1 preserve relationship $2 to $3`. 결과 Map 사용 예: emxProjectBudgetBase_mxJPO.java:1833-1834
:::

## 관계 수정

| 메서드 | 하는 일 | 돌려받는 것 |
| --- | --- | --- |
| `DomainRelationship.setAttributeValue(context, relId, 속성이름, 값)` | 관계 속성 하나를 바꿈 | `void` |
| `DomainRelationship.setAttributeValues(context, relId, map)` | 관계 속성 여러 개를 바꿈. `map` 은 속성 이름 → 값 | `void` |
| `rel.setAttributeValue(context, 속성이름, 값)` | 관계 변수가 있을 때 | `void` |
| `DomainRelationship.setToObject(context, relId, newTo)` | 관계의 to 쪽 객체를 `newTo` 로 바꿈. `modifyTo` 도 같은 일 | `void` |
| `DomainRelationship.setFromObject(context, relId, newFrom)` | 관계의 from 쪽 객체를 `newFrom` 으로 바꿈. `modifyFrom` 도 같은 일 | `void` |
| `DomainRelationship.setType(context, relId, 관계이름)` | 관계의 종류를 다른 관계로 바꿈 | `void` |

```java
DomainRelationship.setAttributeValue(context, relId, attrQty, "3");

DomainObject newChild = DomainObject.newInstance(context, newChildId);
DomainRelationship.setToObject(context, relId, newChild);
```

- `newChildId` 는 바꿔 끼울 하위 부품의 객체 id 입니다.
- `setToObject` 와 `setFromObject` 는 관계를 끊고 새로 만드는 것이 아니라, 있는 관계의 끝 객체를 바꿉니다 (MQL `modify connection`).

::: info 근거
xerinfra.jar `DomainRelationship`: `setToObject` / `setFromObject` 는 MQL `modify connection $1 to $2` / `modify connection $1 from $2`, `modifyTo` / `modifyFrom` 은 이 두 메서드를 그대로 부름. `setType` 은 `modify connection $1 type $2`. static `setAttributeValue(context, relId, attr, value)` 는 `new DomainRelationship(relId).setAttributeValue(context, attr, value)`
:::

## 여러 변경을 한 묶음으로

값을 둘 이상 바꾸거나 만들고 연결하는 것처럼 여러 변경이 함께 성공하거나 함께 취소되어야 하면 트랜잭션으로 묶습니다.

```java
Map attrs = new HashMap();
attrs.put(attrStatus, "Approved");
ContextUtil.startTransaction(context, true);
try {
    part.setAttributeValues(context, attrs);
    part.setDescription(context, "검토 완료");
    ContextUtil.commitTransaction(context);
} catch (Exception e) {
    ContextUtil.abortTransaction(context);
    throw e;
}
```

| 메서드 | 하는 일 |
| --- | --- |
| `ContextUtil.startTransaction(context, true)` | 쓰기 트랜잭션을 시작함. `ContextUtil` 로 이미 열려 있으면 횟수만 셈. 다른 방법으로 연 트랜잭션 안이면 아무것도 안 함 |
| `ContextUtil.commitTransaction(context)` | 변경을 확정함. 가장 바깥에서 부른 것만 실제로 확정 |
| `ContextUtil.abortTransaction(context)` | 변경을 되돌림. 횟수가 0 이 되는 가장 바깥 호출만 실제로 되돌리고, 안쪽은 횟수만 줄임 |

- `catch` 에서 되돌린 뒤 예외를 다시 던져야 부른 쪽도 실패를 압니다.
- 생성 폼, 편집 폼처럼 화면 처리 JSP 가 이미 트랜잭션을 열고 JPO 를 부르는 경우도 있습니다. 그때 JPO 가 예외를 던지면 화면 처리 전체가 취소됩니다 ([트랜잭션](/jpo/transaction-context#트랜잭션)).
